# Карта школьника — дашборд по школьному питанию Калининградской области

Интерактивная страница с двумя контурами. На входе — выбор контура.

- **Город Калининград** — ежедневные продажи операторов питания в школах города. Обороты пересчитаны в транзакции по среднему чеку 150 ₽. Разделы: транзакции по дням, рейтинг операторов, таблица школ, матрица готовности по корпусам, проблемные зоны.
- **Калининградская область** — срез по школам области: привязка карт и ЛК родителей, готовность питания, рейтинг операторов, таблица школ, проблемные зоны. СКУД показан по трём стадиям — оборудование установлено, контроллеры подключены, ПО прогружено; рабочим он считается только когда пройдены все три.

`index.html` — автономная страница, все данные внутри файла, внешних зависимостей нет (шрифты подгружаются с Google Fonts, без них работает на системных).

**Страница собирается автоматически.** Правки нужно вносить не в `index.html`, а в шаблон `build/template.html` — иначе ближайшая ночная сборка их затрёт.

## Как это работает

Раз в сутки скрипт Google Apps Script:

1. заходит в [папку на Google Диске](https://drive.google.com/drive/folders/1q8qx9jrjup346OllQqBrOyKU0ozlM1_w) и находит там два свежих файла `.xlsx`;
2. читает их и собирает данные по обоим контурам;
3. берёт из этого репозитория шаблон `build/template.html`;
4. подставляет данные и публикует `index.html` обратно в репозиторий;
5. GitHub Pages показывает результат.

Если данные не изменились, коммита не будет. Если файл в папке не найден или сломался разбор — скрипт **ничего не публикует**: на сайте остаётся предыдущая версия.

**Чтобы обновить дашборд, достаточно положить новый файл в папку.** Называть его можно как угодно: тип определяется по содержимому, а из нескольких файлов одного типа берётся самый свежий.

### Что показывает контур «Область»

Страница повторяет структуру самой выгрузки: блоки на ней названы так же, как группы колонок в шапке отчёта. В каждом блоке сначала итог по области, потом разрез по школам.

| Блок | Колонки отчёта | Что на странице |
|---|---|---|
| Задачи школы | ЛС, учителя, карты (всего, MIFARE, БК HMAC), ЛК Родителя, интеграция с КЖ, тарифы, ЛС на тарифах | итоги и доли от числа учащихся |
| Задачи организатора питания | активное меню, комплексы, комплексы с тарифами, блюда, заявки | итоги и доли школ |
| Оборудование: питание | обновлено оборудование СБС, кол-во терминалов | «Да» — готово, «Нет» — не готово; число школ и доля готовности |
| Оборудование: СКУД | установлено, контроллеры подключены, ПО прогружено | три стадии по отдельности и доля школ, прошедших все три |
| Транзакции | сумма списаний за питание, кол-во транзакций по картам | итоги, средний чек и 15 школ с наибольшим числом транзакций |

Ниже — привязка карт по муниципалитетам, сводка по операторам питания и таблица школ. У таблицы шесть вкладок: по одной на каждый блок и «Все поля» — там все 30 содержательных колонок отчёта сразу. Не показаны только «Регион» и «Дата»: в выгрузке они одинаковы во всех строках. Таблица сортируется по любому столбцу, ищется по школе, муниципалитету, оператору и ИНН и фильтруется по готовности; клик по муниципалитету или оператору фильтрует её же.

## Установка (делается один раз)

### 1. Токен GitHub

GitHub → Settings → Developer settings → Personal access tokens → **Fine-grained tokens** → Generate new token:

- **Repository access** → Only select repositories → `kindsfater-arch/kaliningrad`
- **Permissions** → Repository permissions → **Contents: Read and write**

Больше ничего включать не нужно. Скопируйте токен — показывается он один раз.

> Токены с ограниченным сроком нужно будет продлить до истечения, иначе сборка начнёт падать.

### 2. Скрипт

1. [script.google.com](https://script.google.com) → **Новый проект**.
2. Скопируйте в него содержимое [appsscript/Code.gs](appsscript/Code.gs) (заменив то, что было).
3. Настройки проекта → часовой пояс **Europe/Kaliningrad**.

### 3. Свойства скрипта

Настройки проекта → Свойства скрипта → добавить:

| Свойство | Значение |
|---|---|
| `GITHUB_TOKEN` | токен из шага 1 |
| `FOLDER_ID` | `1q8qx9jrjup346OllQqBrOyKU0ozlM1_w` |
| `REPO` | `kindsfater-arch/kaliningrad` |
| `NOTIFY_EMAIL` | ваша почта — на неё придёт письмо, если сборка упадёт (необязательно) |

Значения по умолчанию для всех, кроме токена, уже прописаны в начале `Code.gs`, так что задавать обязательно нужен только `GITHUB_TOKEN`.

### 4. Первый запуск

В редакторе выберите функцию **`setup`** и нажмите «Выполнить».

Google попросит разрешения (доступ к Диску и внешние запросы) и покажет экран «Приложение не проверено» — это ваш собственный скрипт: «Дополнительно» → «Перейти к проекту». `setup()` создаст ежедневный триггер на 6 утра и сразу выполнит первую сборку.

### 5. Публикация страницы

GitHub → Settings → Pages → Source: **Deploy from a branch** → `main` / `/ (root)`.

Адрес: **https://kindsfater-arch.github.io/kaliningrad/**

## Эксплуатация

- **Пересобрать вручную** — в редакторе Apps Script выбрать функцию `build` и нажать «Выполнить».
- **Что произошло** — «Выполнения» в левом меню редактора: там видно, какие файлы найдены и что опубликовано.
- **Поменять вёрстку или состав разделов** — правится `build/template.html` в этом репозитории, обычным коммитом. Скрипт подтягивает шаблон при каждой сборке, в Apps Script заходить не нужно.
- **Поменять средний чек** — свойство скрипта `AVG_CHECK` (по умолчанию 150).
- **Поменять время сборки** — свойство `BUILD_HOUR`, затем ещё раз выполнить `setup()`.

### Если сборка падает

**`403: Resource not accessible by personal access token`** на шаге записи. Токену разрешено только чтение. Репозиторий публичный, поэтому читать может любой токен — сборка спокойно доходит до публикации и падает на ней.

Откройте [страницу токена](https://github.com/settings/tokens?type=beta) и проверьте два места:

- **Repository access** — должно быть «Only select repositories» с выбранным `kaliningrad`. Вариант «Public repositories» даёт доступ **только на чтение** и приводит ровно к этой ошибке.
- **Permissions → Repository permissions → Contents** — должно быть `Read and write`, а не `Read-only`.

Права меняются у существующего токена, пересоздавать его не нужно — изменения действуют сразу.

Чтобы не гадать, запустите из редактора функцию **`checkAccess`**: она скажет, кому принадлежит токен, какого он вида и что ему разрешено в репозитории. Ничего не публикует.

**`Проверка не пройдена…`** — сработал заслон: структура выгрузки изменилась, см. раздел ниже. На сайте осталась прежняя версия.

### Что получается на выходе

| Путь | Что это |
|---|---|
| `index.html` | сама страница |
| `data/city.json`, `data/oblast.json` | те же данные в машиночитаемом виде, видны в истории коммитов |
| `data/history/ГГГГ-ММ-ДД.json` | ежедневный срез по области (~4 КБ): итоги, разрезы по муниципалитетам и операторам |

Отчёт по области — это снимок на один день, динамики внутри него нет. Поэтому срезы копятся в `data/history/`: по ним можно будет построить графики роста охвата.

## Разработка

Сборку можно прогнать локально, без Apps Script и без записи в репозиторий:

```bash
node tools/localbuild.js путь/к/Операторы\ питания.xlsx путь/к/Отчет\ Калининград.xlsx
open dist/index.html
```

Результат ложится в `dist/` (папка не коммитится). Второй прогон подряд должен сообщить «данные не изменились» — так проверяется, что сборка детерминирована.

Сверить собранную страницу с эталонной:

```bash
node tools/compare.js dist/index.html index.html
```

Проверки разбора, не требующие файлов (поиск колонок, разбор ячеек готовности, заслон от порчи данных):

```bash
node tools/selftest.js
```

[tools/localbuild.js](tools/localbuild.js) подменяет `DriveApp`, `Utilities` и `UrlFetchApp` заглушками и выполняет тот же самый `Code.gs`, что работает в облаке, — отдельной копии логики нет.

### Что будет, если структура Excel-файлов изменится

Сайт не сломается никогда: при любой ошибке разбора публикация отменяется и на сайте остаётся предыдущая версия. Худшее, что бывает, — дашборд перестаёт обновляться, и приходит письмо (если задан `NOTIFY_EMAIL`).

**Переживёт без правок.** Колонки переставили или вставили новую; файл переименовали; добавился новый день продаж; заранее заготовлены пустые колонки под будущие даты; появился новый оператор, школа или муниципалитет; в книгу добавили лист; в отчёте области сдвинулась строка заголовков; написали «- Да», «-да» или с переносом строки.

**Остановит сборку с понятным сообщением.** Исчезла или переименована одна из обязательных колонок:

| Контур | Обязательные колонки |
|---|---|
| Город | «меню горячего питания», «меню буфета», «составлены комплексы», «начаты продажи» |
| Область | «Город», «Краткое наименование школы», «Наименование КШП» |

Туда же: в файле операторов не нашлось ни одного оператора со школами, нет ни одной заполненной колонки продаж, в отчёте области нет строки заголовков или ни одной школы.

**Не остановит сборку, если колонка пропала или её переименовали.** Вместе с данными публикуется список колонок, которые удалось найти (`found` в `data/oblast.json`). Дашборд его читает и там, где колонки не было, пишет «нет в выгрузке» вместо числа: плитка блока, столбец таблицы и KPI сами говорят, что данных нет. Соврать нулём здесь нечем, поэтому публикация продолжается, а в журнал уходит строка с перечнем пропавших колонок. Так пережили три подряд изменения выгрузки: «Подключено» → «Контроллеры подключены» (18.09), пропажу колонок транзакций (21.09) и их возвращение под новыми именами (23.09).

**Остановит сборку по результату.** Колонка на месте, но все значения в ней обнулились — отличить сломанный разбор от настоящего нуля нельзя, а ноль на странице выглядит как настоящее число. Поэтому публикация отменяется, если показатель, который раньше был ненулевым, обнулился целиком, либо число школ или операторов упало более чем на 30%. Порог щадящий намеренно — задача поймать развал разбора, а не следить за самими данными.

Колонки ищутся сначала по точному совпадению заголовка и только потом по подстроке. Иначе «Город» перехватила бы колонка вроде «Городской округ», а «Подключено» — «Признак подключения интеграции».

### Почему xlsx читается вручную, а не библиотекой

Проверено на реальных файлах, каждый пункт ломает наивный разбор:

1. Файлы сделаны разными генераторами: в одном теги с префиксом (`<s:row>`, `<s:c>`), в другом без (`<row>`, `<c>`).
2. В словаре строк одного файла 569 записей, но 941 тег `<t>` — часть строк разбита на фрагменты. Если считать «один `<t>` = одна строка», сдвинется весь словарь и в дашборд попадут чужие тексты.
3. Пустые строки в XML отсутствуют, поэтому номер строки берётся из атрибута `r`, а не из порядка следования.
4. `openpyxl` эти файлы не открывает вовсе — падает на битом `xl/styles.xml`. Стили здесь не читаются, так что это не мешает.

Колонки продаж в файле операторов дописываются вправо по мере появления новых дней, причём пустые колонки под будущие даты заготовлены заранее. Даты читаются из шапки, пустые колонки отбрасываются — руками поправлять ничего не нужно.
